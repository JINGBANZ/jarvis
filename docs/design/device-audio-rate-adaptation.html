Jarvis · Capture subsystem · Design note

Device-agnostic audio capture & fail-loud startup

Why Jarvis silently refuses to start on AirPods today, the fix that lets capture adapt to any input device without regressing the one-clock echo design, and a single module that makes sure no failure is ever invisible again.

Status: Proposed Date: 2026-06-23 Scope: AggregateEchoCapture.swift · AppDelegate.swift · + UserFacingError / ErrorReporter

01The problem

With AirPods connected as the active microphone, clicking Start does nothing — the menu briefly flips to running, then quietly reverts. No alert, no terminal error.

Capture runs through a single CoreAudio aggregate device (built-in mic clock + system-audio process tap) that is hard-pinned to 48 kHz and verified:

// AggregateEchoCapture.swift:111
guard Self.setNominalSampleRate(agg, 48_000) else {
    jlog("capture — could not pin aggregate to 48 kHz"); teardownAudioLocked(); return false
}

When AirPods are the input, macOS switches them into Bluetooth hands-free (HFP) mode — mono, 16 kHz (sometimes 24 kHz) — and the device does not advertise 48 kHz. The pin fails, the build tears down, and the failure is reported only through jlog + an out-of-band onUnavailable callback.

Confirmed from session logs

built-in mic  → capture started (one-clock mic + system tap @48 kHz, AEC3 on).
AirPods     → capture — could not pin aggregate to 48 kHz

Two distinct defects compound here: a capability bug (we force a rate the device can't do) and a visibility bug (start() returns true unconditionally, so the failure never reaches the user).

02Why it was pinned to 48 kHz — and why it's safe to stop

The pin was deliberate, added in the review-hardening pass of PR #20 (the one-clock AEC work). Its stated rationale:

PR #20 — review commit

“Pin + verify the aggregate at 48 kHz (it otherwise inherits the mic's rate; a 44.1 kHz input would corrupt the echo model and mislabel the wire rate to the transcriber).”

So the pin guards two things — and, importantly, neither of them is the clock:

  • AEC3 rate-match. WebRTCEchoCanceller is created at a fixed jarvis_aec_create(48000). If the aggregate inherited a 44.1 kHz mic and the IOProc's 44.1 kHz samples were processed as if they were 48 kHz frames, AEC3's echo model is fed mislabeled audio and cancellation collapses.
  • Wire-rate label. The 48 kHz → 24 kHz downsampler assumes its input really is 48 kHz. Feed it 44.1 kHz that's labeled 48 kHz and you get 22.05 kHz labeled 24 kHz — pitch- and tempo-warped audio to the transcriber.
The clock is a separate mechanism — and untouched

What actually makes AEC work here is the one-clock aggregate: mic = clock master, system tap drift-compensated onto it, a single IOProc delivering both sample-synced (the two-clock predecessor managed only ~5% cancellation). This change does not touch any of that — still one aggregate, one IOProc, one hardware clock, same drift compensation. We stop forcing the clock's rate; we read it and resample to 48 kHz before AEC. The pin was about rate, not the clock.

Both of the pin's original concerns are better satisfied after the change: AEC3 always receives true 48 kHz (we resample up to it) rather than only working when the device happens to offer 48 kHz, and the downsampler is fed genuine 48 kHz so the wire label stays correct. The far/near lockstep pad simply moves to after the resample. The one residual risk — two independent resamplers staying frame-aligned — is covered by that same lockstep and confirmed by live AEC-dB measurement (see §7). And if the device rate ever can't be read, we fail loud rather than assume 48 kHz — assuming wrong is exactly the corruption the pin guarded against.

03The design

Part A — Adapt to the device's native rate

Stop pinning. After the aggregate is built, read its actual nominal sample rate, and resample the incoming mic + tap up to a fixed 48 kHz internal rate that AEC3 runs at. The wire stage (48 kHz → 24 kHz for transcription) is unchanged.

Before — pinned

✕ pin aggregate → 48 kHz (fails on AirPods)
→ mic 48k ─ AEC3 ─ clean 48k
→ tap 48k ─ AEC3 reference
→ down 48k → 24k → wire

After — adaptive

✓ read aggregate rate R (any)
→ mic R → up→48k ─ AEC3 ─ clean
→ tap R → up→48k ─ reference
→ down 48k → 24k → wire
  • The up-resamplers are optional. When the device is already 48 kHz (built-in mic), they are nil and the hot path is byte-identical to today — zero behavior change for the common case.
  • AEC3 stays fixed at 48 kHz. Its echo model, 480-sample (10 ms) framing, and constants never change. Only the input rate varies, and it's normalized before AEC sees it.
  • Route changes adapt for free. buildAudioLocked re-reads the rate, so plugging AirPods in mid-session now rebuilds and adapts instead of failing.
  • The framers absorb the new counts. PCM16Framer already accumulates arbitrary input into whole 480-sample frames; Resampler already carries filter state across calls. The far/near lockstep pad moves to after resampling, at 48 kHz.

Part B — One module owns every user-facing error

Rather than scatter NSAlert + stop() logic across call sites, all failures flow through a single error module. This follows the repo's “logic in Core, OS-glue thin on the outside” rule and gives one place that owns how a failure is surfaced.

JarvisCore — model

· UserFacingError (Sendable)
· title · message
· severity: fatal / degraded / info
· Foundation-only · unit-testable

JarvisApp — presenter

· ErrorReporter (@MainActor)
· one entry: report(_:)
· any thread → hops to main
· the only place NSAlert exists

Severity drives the response — call sites just report; the module decides:

SeverityResponseUsed by
FATALNSAlert + stop session + menu → stoppedmissing API key · capture build failure · mic-socket terminal failure · route-rebuild failure
DEGRADEDlog / subtle note · no modal · session continuessystem-audio (“them”) socket gives up — mic still works
INFOlog onlyadvisory notices
  • Every failure routes through report(_:) — including the graceful “them”-socket degrade. It still goes through the module; the module just decides not to shout. That's the single-funnel discipline you asked for.
  • warnNoKey collapses into a FATAL UserFacingError — no more bespoke inline alert.
  • start() stops returning true unconditionally: a capture-build failure reports FATAL and returns false, killing the silent menu-flip.
Boundary with JarvisLog

ErrorReporter owns user-facing surfacing + session-lifecycle consequence. Diagnostics stay in JarvisLog/jlog, which already centralizes the debug + activity logs. Two cohesive responsibilities — surfacing vs. logging — rather than one module doing both. (Open question for review: keep them split, or funnel logging through the same module too?)

04What does upsampling to 48 kHz cost?

Inserting a R → 48 kHz resample in front of AEC has real but small costs — and one honest limitation that isn't ours to fix.

  • Latency — negligible. AVAudioConverter's filter delay is a few milliseconds at most. Both mic and tap get the identical delay (same config), so AEC's far/near alignment is preserved, and a few ms is nothing against Jarvis's seconds-scale hint pipeline.
  • CPU — trivial. Two extra resample passes per IOProc callback on non-48k devices — and zero on the built-in 48 kHz path, where the up-resamplers are nil.
  • Resampling artifacts — imperceptible. The full chain on AirPods is 16k → 48k → AEC → 24k. AVAudioConverter is a high-quality sinc resampler; the double conversion adds nothing audible.
Honest limitation — inherent, not caused by this change

AirPods used as a mic run in Bluetooth HFP narrowband (~8–16 kHz). That audio is low-fidelity the moment it's captured; upsampling to 48 kHz can't recover bandwidth that was never there. This change stops blocking the device — it does not make the AirPods mic sound good. The only real fidelity fix is AirPods for output, built-in mic for input, which is worth surfacing to the user as guidance (an INFO/DEGRADED notice), separate from this work.

05Do AirPods even need AEC3?

No — and that's worth being precise about. Acoustic echo cancellation exists to remove far-end audio (the remote caller / system sound) that leaks out of your speakers and back into your mic. With AirPods the speakers are sealed in your ears, so essentially nothing leaks back. On that route AEC3 has no echo to remove and runs as a near-passthrough.

So why keep it on?

Because “this route is echo-free” can't be detected reliably. A Bluetooth speaker presents to CoreAudio identically to a Bluetooth headset — same transport type, same device class. If we bypassed AEC whenever we thought we saw headphones, we'd let full-volume echo back in the moment someone is actually on a Bluetooth speaker. Running AEC3 as a cheap passthrough on earbuds is strictly safer than guessing wrong.

This is exactly why the chosen design resamples AirPods audio up to 48 kHz for AEC rather than routing around it: the path stays uniform and route-detection-free. The cost — upsampling band-limited 16 kHz audio into a 48 kHz container so a passthrough can run over it — is negligible. (See Alternative C, which does bypass AEC, and why it loses.)

06Alternatives considered

ApproachIdeaVerdict
A. Read native → resample to 48kChosen Don't pin. Read the device rate, upsample to a fixed 48 kHz for AEC. One uniform path covers every device.
B. Run AEC at the device's native rate Query supported rates, pick an AEC3-legal one (16/32/48k), reconfigure AEC + framing to match. Doesn't generalize — see below.
C. Detect headphones, bypass AEC On a headphone/AirPods route, skip AEC entirely and resample device → 24k directly. Unsafe detection.
D. Keep pinning, just alert on failure Leave the 48 kHz pin; only fix the silent-failure half. Leaves AirPods unusable.

A — Read native, resample to 48k (chosen)

  • Handles every device with a single code path — AirPods (16/24k), USB interfaces, external DACs (44.1k), built-in (48k).
  • AEC3 config is invariant: no per-device frame-size, model, or rate juggling — the most error-prone part stays frozen.
  • No route detection anywhere; nothing to misclassify.
  • Zero change to the proven 48 kHz built-in path (resamplers are nil there).
  • Two extra resample passes per callback on non-48k devices (cheap, and off the built-in path).
  • Upsampling 16 kHz to 48 kHz doesn't add real bandwidth — but nothing in the pipeline needs it to; it's a container rate.

B — AEC at native rate

  • Doesn't actually generalize. AEC3 accepts only 8/16/32/48 kHz. AirPods can run at 24 kHz and gear at 44.1 kHz — neither is legal, so you resample anyway. You'd add complexity and still need the fallback.
  • Variable AEC frame size and wire-resampler ratio multiply the edge cases in the most delicate component.
  • Slightly less resampling in the lucky case where the device rate is already 16/32/48k.

C — Detect headphones, bypass AEC

  • Skips AEC and one resample on earbud routes — technically the lightest path when it's right.
  • Detection is unreliable: a Bluetooth speaker looks identical to a headset. A wrong bypass readmits full echo — the exact failure AEC exists to prevent.
  • Adds a route-classification branch the rest of the system deliberately avoids (see the standing note in AggregateEchoCapture.swift on not detecting headphones).

D — Alert only, keep the pin

  • Smallest possible change; makes the failure visible immediately.
  • AirPods (and any non-48k device) still can't be used — it documents the wall instead of removing it. Half the ask.
Why A wins

It's the only option that makes capture genuinely device-agnostic while keeping AEC3 — the riskiest moving part — completely frozen, and without introducing any route detection that could silently misfire. Fail-loud (Part B) ships alongside it regardless, so a future device we can't support announces itself instead of hiding.

07Verification

JarvisApp is intentionally not unit-tested — the capture path needs live TCC permissions, a real mic, and screen capture. The new UserFacingError model is Foundation-only and unit-tested in Core. The capture change is verified live, per the smoke checklist:

  • Built-in mic → Start → confirms capture starts and transcription flows (unchanged 48k path).
  • AirPods connected as input → Start → capture starts, transcription flows, no could not pin line; swap routes mid-session and confirm a clean rebuild.
  • No echo regression: on a non-48k device on speakers, confirm AEC still measures the expected 30–50 dB cancellation (the resampled far/near stay aligned) — measured, not assumed.
  • Force failures (deny mic permission; unreadable device rate) → confirm the NSAlert fires via ErrorReporter and the menu returns to stopped.
